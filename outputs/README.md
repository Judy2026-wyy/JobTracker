# 求职追踪看板（Job Tracker）

基于 Streamlit + SQLite 的求职投递/面试进度追踪应用。

## 功能

- 上传截图或直接从剪贴板粘贴截图：两种方式并排放在**同一个方框**里（「方式一：
  从电脑里选图片」/「方式二：粘贴剪贴板里的截图」），不需要先切换选择用哪种，
  可以混着用。支持一次提供多张图片，大模型会把这些图片放在一起综合识别
  （同一条记录拆在几张图里的会自动合并，多条不同记录会自动拆分），
  逐条核对、可勾选跳过后一次性保存
- 截图识别会把岗位核心信息**完整提炼进备注**（工作地点、部门、招聘类型、学历与经验
  要求、薪资、技能要求、投递渠道、截止日期、职位编号、志愿顺序等），按「字段：值」
  逐行罗列，以后回看不用再翻截图；提示词里明确**禁止编造和扭曲事实**——只写截图里
  真实出现的内容，不用常识补全、不改写数字与日期、看不清的直接不写也不猜
- 上传/粘贴的图片统一压成**正方形缩略图**（等比缩放 + 居中留白，不裁切，
  竖长的手机截图也能看清内容），排成整齐的图片墙；**点击图片本身即可选中**，
  选中的图片会描上绿色边框并打 ✅，不用再去勾选框。工具栏提供「删除选中的图片」、
  「批量删除（清空全部）」和「全选 / 全不选」
- 连接 163 邮箱（IMAP），自动解析邮件中的投递/面试进度更新，预览确认后导入；
  候选记录按邮件类型（笔试 / 面试 / offer通知 / 其他）分 tab 展示，不想入库的
  邮件可以「跳过」（本次不导入、仍留在原分组）或「忽略」（本次不导入、并归到
  「其他」分组），两种操作都能一键恢复，且都不会动 163 邮箱里的原始邮件
- 投递去重：邮件里的公司名和库里写法不一样（「德勤」/「德勤中国」/「Deloitte」）时，
  会**先问你是不是同一次投递**，是则在原记录上更新状态而不是新增一条
  （详见下方「投递去重」一节）
- SQLite 本地数据库记录投递（applications）与面试（interviews）
- **时区设置**（侧边栏，「关闭应用」上方）：选国家/地区决定面试时间怎么展示。
  选「中国」全境统一用北京时间、不再追问城市；选其他国家会再问一次城市/地区
  （美国分东部/中部/山地/太平洋等档位），自动换算成对应时区。设置存进数据库，
  重启后仍然生效，首页提醒、面试月历、邮箱同步预览、看板日期全部跟着变
- 首页提醒条：未来 48 小时内的面试，按时间升序展示（按你选定的时区显示本地时间，
  并在时间后标出当前时区）；时区未确认的记录单独分组，标注"时间待确认"
- 首页投递趋势折线图：X 轴为投递日期、Y 轴为当日投递数，默认展示近一周走势，
  可切换统计周期（最近7/30/90天或全部），悬停查看具体某天的投递数
- 投递看板「投递漏斗分析」：最上层是总投递数、最底层是拿到 offer 的数量，
  中间依次是笔试 / 一面 / 二面 / 三面，每层一个颜色、标出人数和占总投递的比例，
  下方明细表给出每一层「较上一阶段转化率」，一眼看出卡在哪一环
  （口径与层级设计见下方「投递漏斗分析」一节）
- 月视图日历（streamlit-calendar），展示所有面试卡片，支持切换月份查看历史
- 简单统计：各状态数量、投递→面试转化率
- 状态严格按枚举流转：已投递 → 简历筛选中 → 笔试 → 一面 → 二面 → 三面 → HR面 → 已收offer，
  任意阶段可转为 已拒绝 / 已终止；10 个状态的颜色经过 OKLab 色差校验，确保彼此
  能明显区分，不会出现"看起来都差不多"的相近色
- 投递看板「最大间隔天数」按完整天数（整数）统计，不出现带小数的天数
- 岗位分类采用 29 个一级类目的职能分类体系（后端开发 / 前端开发 / 算法 /
  AI大模型 / 数据 / 产品 / 设计 / 运营 / 财务 / 法务合规风控 …），并把类目下的
  典型岗位关键词和一套消歧规则一起写进 LLM 提示词，让大模型分类更准更稳定
- 侧边栏底部提供「🛑 关闭应用」按钮（带二次确认），不熟悉命令行也能直接在
  网页上安全地关闭应用

## 本地部署步骤

### 1. 准备环境

需要 Python 3.10 及以上版本（`zoneinfo` 与部分类型标注语法要求）。

```bash
python3 --version   # 确认 >= 3.10
```

### 2. 创建虚拟环境并安装依赖

```bash
cd job_tracker  # 进入本项目所在目录
python3 -m venv .venv
source .venv/bin/activate     # Windows 用 .venv\Scripts\activate
pip install -r requirements.txt
```

### 3. 配置环境变量

```bash
cp .env.example .env
```

编辑 `.env`，填入：

- `LLM_API_KEY`：OpenAI API Key（用于截图识别与邮件解析，调用 GPT-4o）
- `IMAP_HOST`：163邮箱 IMAP 服务器，默认 `imap.163.com`
- `IMAP_USER`：163邮箱完整地址
- `IMAP_PASS`：163邮箱的 **IMAP 授权码**（不是登录密码，需在163邮箱设置里单独开启 IMAP/SMTP 服务并生成授权码）

> 应用代码中已通过 `load_dotenv(find_dotenv(), override=True)` 加载 `.env`，无需额外配置。

### 4. 启动应用

```bash
streamlit run app.py
```

启动后浏览器会自动打开 `http://localhost:8501`。

### 5. 首次使用

1. 打开「全部记录」手动新增几条投递记录，或在「上传截图」中选择文件上传（可一次
   选多张），也可以先复制截图到剪贴板，切到「📋 粘贴截图」标签页，点击按钮后按
   Ctrl+V（Mac 为 Cmd+V）粘贴，可重复粘贴多张；多张图片会一起交给大模型综合识别，
   同一条记录拆在几张图里的会自动合并，不同记录会自动拆分；传错了可以勾选后
   「删除选中的图片」，或直接「清除全部图片」重来；或直接同步邮箱
2. 「邮箱同步」点「开始同步」后，候选邮件会按 笔试 / 面试 / offer通知 / 其他
   四个 tab 分组列出：想入库的保持勾选，不想入库的点「⏭️ 跳过」或
   「🚫 忽略（归到其他）」，点错了再点「↩️ 恢复」即可；最后点「导入勾选的记录」
3. 在「添加面试安排」中填写面试时间和时区，未确认时区的会出现在首页"时间待确认"分组
4. 「面试月历」可切换月份查看历史与未来的面试安排
5. 首页「投递趋势」折线图可以切换统计周期，看看自己最近投递节奏怎么样

## 时区设置

面试最怕时间看错，所以展示时区做成了可选项（侧边栏「时区设置」，在「关闭应用」
按钮上方），选完立刻生效并存进数据库的 `app_settings` 表，重启后仍是这个时区。

- **选「中国」**：中国全境行政上统一使用北京时间（UTC+8），所以不再追问城市，
  直接用 `Asia/Shanghai`。
- **选其他国家**：再问一次城市/地区，据此自动换算出时区。跨时区的国家按时区
  档位给城市（美国分东部/中部/山地/太平洋/阿拉斯加/夏威夷，加拿大、澳大利亚同理），
  照着自己所在城市选即可。
- **列表里没有的地方**：选「其他（手动填时区名）」直接填 IANA 时区名（形如
  `Europe/Madrid`），填错会当场提示，不会存进库。

底部会显示当前时区、UTC 偏移和该时区下的当前时间，方便确认选对了没。

数据层的口径没变：数据库里一律存 UTC，只有展示时才换算，所以**改时区不会动
任何已保存的数据**，同一条面试记录在不同时区下只是显示成不同的当地时间。
夏令时由 zoneinfo 按日期自动处理（芝加哥夏天 CDT、冬天 CST；伦敦夏天 BST、
冬天 GMT），不硬编码 UTC±N 偏移量。

注意区分两个"时区"：
- **展示时区**（这里选的）：所有面试时间显示成哪里的时间。
- **来源时区**（「添加面试安排」表单里填的、邮件解析出来的）：面试通知里那个
  时间本身属于哪个时区。国内公司发来的邮件如果没写时区，默认按北京时间解释
  （`config.DEFAULT_SOURCE_TIMEZONE`），并标记为"时区待确认"等你核对。

## 投递漏斗分析

投递看板顶部的漏斗图：最上层是总投递数，最底层是拿到 offer 的数量，中间依次是
笔试 → 一面 → 二面 → 三面，每层一种颜色，块上标人数和占总投递的比例，
下方明细表给出每层「较上一阶段转化率」和「本层流失」。

**统计口径是「至少走到过这一层」**，每条投递取它历史上到过的最深阶段
（`status_history` 里所有非终止状态的最大深度），而不是当前状态——状态一旦转成
已拒绝/已终止就把之前的进度覆盖掉了，只看当前状态的话，"走到三面才被拒"会被
算成"没进过面试"，漏斗就失真了。所以走到过笔试后被拒的投递，仍然计入笔试这一层。

层级相对状态枚举做了三处裁剪（只影响这张图，不影响状态流转本身，见
`config.FUNNEL_STAGES` 的注释）：

1. **「已投递」与「简历筛选中」合并成同一层**——简历筛选是投递之后的被动等待，
   分成两层看不出转化，合并后第一层就等于总投递数。
2. **去掉「HR面」层**。但 HR面 仍然计入深度：走到 HR面 的投递会被算进「三面」层
   （它确实已经走过了三面），只是不单独占一层。
3. **去掉「已拒绝」层**。被拒不是漏斗的一层，而是每一层的流失，它体现在下一层
   人数的减少上；单独列一层会把转化率算重。

漏斗同样受页面顶部的日期范围、岗位分类筛选影响，可以只看某一批投递的转化情况。

## 投递去重

同一次投递常常从多个渠道重复进来：截图里写「德勤」，邮件署名却是「德勤中国」，
隔几天又来一封面试邀请。三道防线保证它在数据库里只占一条记录。

### 1. 数据层兜底（截图 / 邮件 / 手动新增都生效）

`db.upsert_application()` 在插入前先按归一化后的**公司名 + 岗位名**查一次
（`db.find_normalized_duplicate`，不看投递日期），命中就返回已有记录的 id 而不新建。
归一化规则见 `dedup.normalize_company` / `normalize_position`：

- 去掉括号内容（`安永（中国）企业咨询有限公司` → `安永企业咨询`）
- 去掉组织形式后缀：`有限公司`/`集团`/`控股`/`Ltd`/`Inc`/`LLC`…（英文按整词删，
  不会把 `Cisco` 削成 `Cis`）
- 去掉**结尾**的地域词：`德勤中国` → `德勤`。注意只删结尾的，`中国银行` 的「中国」
  在词首、属于名字本身，不会被删
- 岗位名去掉招聘季/批次噪声（`2026届`、`校招`、`毕业生计划`…）

用户明确回答「这不是同一条」时，这层会被 `allow_duplicate=True` 跳过。

### 2. 邮件导入时询问用户

同步邮件解析出候选记录后，逐条与库里已有投递比对（`dedup.suggest_match`）：

- **规则层**：归一化后公司和岗位都对得上 → 直接判定为同一次投递，不花 API 调用。
- **大模型层**：像但不敢确定时才调用。`PwC` 与 `普华永道`、`Deloitte China` 与
  `德勤` 这类中英文写法字符串相似度是 0，只有大模型认得出，所以候选筛选除了
  「公司名够像」，还会放行「岗位名够像」的记录（`POSITION_ONLY_CANDIDATE_MIN`），
  否则它们根本没机会被送到模型面前。模型返回的 id 不在候选里会被丢弃（防编造）。
- 大模型不可用（没配 Key、网络不通、返回不是 JSON）时**自动降级**到规则层，
  只在综合相似度足够高时才提示，并在理由里说明模型不可用。

判出疑似重复后，卡片上会直接**问你**「这封邮件说的是同一次投递吗」：

- 选「✅ 是同一条投递」：不新建记录，把已有记录的状态往前推（`db.advance_status`，
  允许一次跨多个阶段——投完简历直接收到二面通知是常事——但**绝不倒退**，
  避免一封迟到的旧邮件把已经到 HR 面的记录打回「已投递」）；邮件主题和备注以
  `【邮件同步 日期】…` 的形式追加到原记录备注（不覆盖截图提炼的岗位信息）；
  邮件里带的面试时间也挂到原记录名下。
- 选「🆕 不是同一条」：正常新建一条记录。

同一次同步里若有好几封邮件说的是同一条投递（笔试通知 + 面试通知），后面的会自动
并到前面那条上，不会登记两遍。页面上的「用大模型判断」开关可以关掉，关掉后只用
归一化规则比对，不消耗 API 调用。

### 3. 已有重复数据的清理

「全部记录」页面的 **🧹 重复投递记录检查与合并** 折叠面板会扫出历史遗留的重复记录：

- **完全重复**：归一化后公司名 + 岗位名一致的成组展示。
- **疑似重复**：写法差得更远、归一化后不完全一致但相似度很高的成对展示
  （附公司/岗位相似度），需要人工确认。

选一条保留即可合并（`db.merge_applications`）：面试安排和状态流转历史全部改挂到
保留的那条名下（一条都不丢），状态取进度更靠前的，投递日期取更早的，备注拼接，
投递链接/分类空缺时用被合并记录的值补上。

## 岗位分类体系

分类定义集中在 `config.py` 的 `JOB_TAXONOMY`（类目 -> 典型岗位关键词），
`CATEGORIES` 由它直接展开，改分类只需要动这一处。

设计原则：

1. **单一维度**——只按「职能」切分，不混入行业/技术栈/职级。
2. **互斥优先**——相邻类目给出边界说明（`DISAMBIGUATION_RULES`），减少模型摇摆。
3. **可扩展**——新岗位先进已有类目，某个方向的记录多到需要单独看时再升为一级类目。
4. **兜底保留**——「其他」永远排在最后且不给关键词，强制模型先尝试其他类目。

提示词里除了类目名，还会带上每个类目的典型岗位关键词和消歧规则（由
`build_category_prompt_block()` 拼装，截图识别与邮件解析共用同一份，不会两边写岔）。

`normalize_category()` 做了多层兜底，依次尝试：合法类目名 → 旧类目名映射 →
关键词精确匹配 → 关键词子串匹配（长词优先），全都不中才落到「其他」。
这样即使模型输出的是 `后端工程师`（关键词而非类目名）或 `Java后端开发工程师`
（带修饰的岗位名），也能正确归到「后端开发」，而不是白白丢成「其他」。

### 用大模型重新归类历史记录

「全部记录」页面的 **🔄 用当前分类体系重新归类历史记录** 折叠面板，可以把已入库的
记录交给大模型按当前分类体系重新判定（`category_classifier.py`）：

- **处理范围**可选「只处理没归好类的」（旧类目遗留值 + 被归成「其他」的）或「全部记录」。
- 一次请求**批量**处理多条（默认 40 条一批），不会逐条调用，省 token 也快。
- 结果先以 `原分类 → 建议分类` 的形式列出来预览，逐条可取消勾选，
  **确认后才写库**，跟截图识别、邮箱同步保持同一套"预览-确认"逻辑。
- 模型没给出结果的记录会保持原样不动，不会被硬塞一个「其他」覆盖掉原本可能是对的分类；
  模型若编造了不存在的记录 id 也会被丢弃。

### 历史数据迁移

`db.init_db()` 启动时会自动调用 `_migrate_legacy_categories()` 回填旧分类
（如 `测试` → `测试/质量保障`、`人力` → `人力资源`），可重复执行、不会重复改写。

但 `开发`、`算法/AI`、`市场/销售`、`人力/财务/行政` 这几个旧类目属于**一对多拆分**，
无法自动判断该归到哪个新类目（比如「开发」可能是后端/前端/客户端/嵌入式），
迁移时会**保持原值不动**——自动猜一个大概率是错的，宁可留着让你自己改，或者
重新识别一次那条记录。这些没迁移的旧值仍然会出现在筛选器选项的末尾，不会因为
「不在新类目列表里」就被静默过滤掉。

- **长期在服务器/云主机上运行**：建议用 `systemd` 或 `pm2`/`supervisor` 常驻进程，

## 已知限制 / 注意事项

- LLM 识别结果可能有误，截图识别与邮件解析结果均设计为"预览-确认"后再写入数据库，
  请务必人工核对公司名、岗位名、状态与时间。
- 163 邮箱 IMAP 需要账号中显式开启 IMAP/SMTP 服务，并使用授权码而非登录密码；
  客户端必须在 `LOGIN` **之前**成功发送 `ID` 命令自报身份，否则会收到
  `SELECT Unsafe Login` 报错。这里有个不太直观的坑：Python `imaplib` 内置的
  命令状态校验表里根本不认识 `ID` 这个命令，直接调用会在写 socket 之前就抛
  `KeyError`，如果外层用宽泛的 `except Exception` 包住，会把这个报错静默吞掉、
  误以为"ID 已经发送但服务器不需要"，实际上 ID 从来没有发出去过。本项目已在
  `email_import.py` 里把 `"ID"` 注册进 `imaplib.Commands` 再发送，正常情况下
  无需手动干预。
- 若同步时报 `LOGIN Login error or password error`，说明是账号/密码认证本身
  失败（跟上面的 ID 顺序问题是两回事），请逐项检查：`IMAP_USER` 是完整邮箱
  地址；`IMAP_PASS` 是163邮箱「设置 - POP3/SMTP/IMAP - 客户端授权密码」页面
  生成的授权码而非登录密码；如果最近重新生成过授权码，需要把 `.env` 里的值
  同步更新，并确认复制时没有带上多余的空格或引号（代码已对读到的值做了
  `strip()` 防御处理，但 `.env` 文件本身的内容需要你自己确认）。
- 邮件中若未明确写出时区，程序默认按 `Asia/Shanghai`（北京时间）解释原始时间，再换算成
  你在侧边栏选定的展示时区，且该记录会被标记为 `timezone_confirmed=False`，需要人工确认。
- 时区设置是**全局**的，不是每条记录各自一个时区：换了时区，所有面试时间都跟着换算。
  数据库里存的一直是 UTC，改时区不会修改任何已保存的数据。
- 转化率统计口径：已产生至少一条面试记录的投递数 / 总投递数（不依赖 status 字段，
  因为状态一旦转为"已拒绝/已终止"会覆盖此前的阶段信息）。
- `job_tracker.db` 请放在本地磁盘目录下运行（不要放在网络盘/云同步盘的实时同步路径中），
  部分网络文件系统对 SQLite 的文件锁支持不好，可能报 `disk I/O error`。
- 「粘贴截图」功能基于浏览器剪贴板 API，需要在 `https://` 或 `localhost` 环境下使用；
  部分浏览器首次使用时会弹出剪贴板读取权限确认，允许即可。
- 页面右上角的「Rerun / Clear cache / Settings」等开发者菜单和对应的键盘快捷键
  （Streamlit 默认单独按 `c` 键即可触发"清除缓存"）已通过 `.streamlit/config.toml`
  的 `toolbarMode = "viewer"` 关闭，避免用 Ctrl+C 复制页面文字时误触发清除缓存
  确认框。补充说明：本应用没有使用 `st.cache_data` / `st.cache_resource`，所有
  投递/面试记录都在 `job_tracker.db` 这个 SQLite 文件里，即使触发"清除缓存"也
  不会丢失任何已保存的数据。
- 想关闭应用时，点侧边栏底部的「🛑 关闭应用」→「✅ 确认关闭」即可（会有一次
  二次确认，防止手滑点错），不需要去命令行或任务管理器里找进程。关闭后浏览器
  标签页可以直接关掉，下次要用再重新 `streamlit run app.py` 启动。
- 去重是**按公司名 + 岗位名**判断的，同一家公司同一个岗位如果隔了很久重新投一次
  （比如去年投过、今年再投），会被当成同一条投递。确实需要分开记两条时，
  在邮件导入的询问里选「不是同一条」，或手动改一下岗位名做区分。
- 图片墙的「点击图片选中」依赖一段注入的 CSS 把按钮铺满卡片。万一将来 Streamlit
  改了 DOM 结构导致这段样式失效，卡片下方会退化成一个普通的「选择 / 取消选择」
  按钮，功能不会坏，只是没有"点图就选中"那么顺手。
